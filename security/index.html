SECURITY & TRUST ARCHITECTURE

Security is part of the operating model.

Infrastructure Product Works is designed around bounded authority, deterministic validation, verifiable evidence and explicit human authorization. Proposal, validation, review, authorization and infrastructure execution are intentionally separate jobs.

THE GOVERNING RULE

No stage inherits authority merely because the previous stage passed.

A valid request is not an approval. A PASS result is not deployment permission. A product definition is not production authority. A review surface is not a decision engine. Authorization must remain explicit all the way to the point where an authorized control plane is permitted to act.

END-TO-END TRUST MODEL

Every surface has a job. None quietly becomes the whole control plane.

These products can participate in one governed infrastructure journey, but this diagram is a trust model rather than a claim that every deployment uses one rigid runtime sequence.

CORE SECURITY CONTROLS

The architecture is designed to reduce invisible trust.

The goal is not to make automation powerless. It is to make every meaningful capability explicit, bounded and reviewable.

LEAST AUTHORITY

Access follows the declared role

Validation, product construction, review and reconciliation should receive only the permissions required for their bounded responsibility.

DETERMINISM

Policy-sensitive gates stay testable

Security-sensitive decisions favor versioned, repeatable rules over unconstrained model judgment or hidden discretionary state.

PROVENANCE

Evidence stays tied to its source

Producer revision, digest, product binding and decision context are retained so downstream consumers can verify what they are relying on.

FAIL CLOSED

Unverifiable does not become trusted

Identity, evidence, source binding, scope or policy that cannot be verified should stop, hold or require explicit review rather than silently continue.

CUSTOMER CONTROL

Production authority stays with the operator

Credentials, branch protection, enterprise identity, production approvals and operational controls remain customer-owned boundaries.

NO IMPLICIT DEPLOYMENT

A result is evidence for a decision

Guard findings, Forge artifacts and Console review context do not themselves approve, merge, provision or reconcile infrastructure.

ISOLATION

Customer context must travel end to end

Multi-customer design carries customer, organization and environment context through identity, profiles, evidence, approvals, products, secrets, integrations and audit history. Cross-customer substitution must fail closed before any tenant-isolation claim.

PORTABILITY

Trust cannot depend on public internet assumptions

GHES, private runners, private certificate authorities, proxies, mirrors and disconnected verification are treated as security and portability requirements, not deployment trivia.

SEPARATION OF DUTIES

Presentation does not become authority

Review and visibility can be centralized without collapsing producer ownership, formal approval or infrastructure execution into one application.

EVIDENCE INTEGRITY & PROVENANCE

Trust the exact thing that was evaluated, not something that merely looks similar.

The evidence model is intended to preserve a verifiable chain from source to review so later systems can detect substitution, drift or broken lineage.

01

Source revision

Identify the exact proposal, repository state or producer revision that generated the evidence.

02

Evidence digest

Bind the report or assessment output to an integrity value that downstream consumers can verify.

03

Product binding

Retain the selected infrastructure product, contract or product context associated with the evidence.

04

Decision context

Present the verified lineage to reviewers without rewriting the producer verdict or inventing new authority.

What should fail closed?

Mismatched source revisions, broken digests, stale or substituted evidence, missing required authority, scope expansion and cross-customer substitution are all conditions that should stop an automated path or route it to explicit review rather than being normalized away.

AUTHORITY MODEL

Proposal, validation, review, authorization and execution are different verbs for a reason.

Keeping these responsibilities distinct prevents useful automation from quietly becoming an all-powerful deployment system.

STAGE
WHAT IT MAY DO
WHAT IT DOES NOT MEAN
Proposal
Describe desired infrastructure or a product selection.
No approval, credential or deployment authority is implied.
Validation
Evaluate bounded rules and produce evidence-backed findings.
PASS is not permission to merge, remediate or provision.
Construction
Define and render governed product artifacts and contracts.
A valid product artifact is not a production authorization.
Review
Organize verified context, materiality and human workbench information.
A dashboard or review marker is not an approval engine.
Authorization
Grant bounded permission through accountable customer-controlled authority.
Delegated scope may stay equal or narrow; it must not silently widen.
Reconciliation
Drive observed infrastructure toward an authorized desired state.
The reconciler does not retroactively create the authority it consumes.

AI & AGENT SAFETY

AI can increase implementation capacity without inheriting decision rights.

Infrastructure Product Works treats generated infrastructure and AI-assisted recommendations as proposals to validate, not authority to trust simply because a model produced them.

AI MAY

Propose and explain

AI can assist with requirements, mappings, infrastructure-product configuration, implementation drafts, impact analysis and explanations against versioned inputs.

DETERMINISTIC SYSTEMS

Validate what matters

Architecture, policy, security, evidence and authority checks that protect the operating boundary remain explicit, testable and independently verifiable.

HUMANS RETAIN

Accountable acceptance

Material exceptions, approvals, authorization and production decisions remain with the people and systems that own those responsibilities.

FUTURE AGENTS

Bounded commands only

Agent-operated infrastructure remains conditional on explicit authority, least privilege, deterministic guardrails, evidence retention, rollback and escalation.

NO SILENT EXPANSION

Capability does not equal permission

An agent being technically capable of an action does not make that action authorized. The authority package must remain independently checkable.

EVIDENCE

The actor is not the only witness

High-impact automated decisions should leave evidence outside the unilateral control of the component that proposed or performed the action.

RESTRICTED-NETWORK & ENTERPRISE OPERATION

The security model must survive outside a public-cloud demo path.

Portability work explicitly considers GitHub Enterprise Server, private runners, private certificate authorities, proxies, internal mirrors, local evidence handling and reduced or disconnected network conditions.

What the architecture is proving

  • Dependencies are identified instead of assuming unrestricted internet access.
  • Evidence can be imported, verified and reviewed without turning remote collection into a hidden requirement.
  • Private CA, proxy, mirror and runner constraints are treated as first-class operational inputs.
  • Product boundaries remain explicit when adapters and provider integrations change.

What this does not claim

  • Universal operation in every enterprise network or GHES topology.
  • Production authorization merely because restricted-network tests pass.
  • Customer identity, audit, Crossplane or cloud-provider integrations before they are individually accepted.
  • Operational readiness without customer-selected evidence in the target environment.

SECURITY MATURITY

Evidence is separated from aspiration.

The portfolio deliberately distinguishes accepted or demonstrated controls from active validation and future gated capability. A polished preview is not treated as production proof.

ACCEPTED / DEMONSTRATED BASELINE

Bounded trust controls

  • Explicit separation of validation, review, authorization and reconciliation.
  • Deterministic Guard behavior and evidence-oriented product contracts.
  • Console source-revision and digest verification concepts in the current bounded baseline.
  • Assurance synthetic proofs for authority attenuation, custody and independent evidence.
  • Synthetic connected-app paths that stop at human review rather than provisioning.
ACTIVE VALIDATION

Enterprise and customer-operational trust

  • GHES and restricted-network portability.
  • Trusted profile approval and versioning.
  • Customer-selected assessor evidence and operational profiles.
  • Customer identity, persistence, audit and replaceable integration boundaries.
  • Operational evidence sufficient to support an explicit customer decision.
GATED / FUTURE

Do not claim before proof

  • Multi-customer isolation before cross-customer substitution tests pass.
  • Broad autonomous remediation or agent-operated infrastructure.
  • Production authorization inferred from synthetic proofs or documentation.
  • Universal provider, network or enterprise topology compatibility.
  • Any capability that would widen authority beyond an accepted bounded contract.

SHARED RESPONSIBILITY

Infrastructure Product Works can bound the system. The operator still owns the environment.

Infrastructure Product Works

  • Defines bounded product and authority contracts.
  • Builds deterministic validation and evidence semantics within each accepted product scope.
  • Preserves explicit separation between proposal, review and execution.
  • Documents known limitations and evidence-bounded maturity.
  • Provides security reporting guidance for supported product surfaces.

Customer / platform operator

  • Owns enterprise identity, credentials, secrets and production access.
  • Configures branch protection, repositories, runners, network controls and operational policy.
  • Selects the authoritative control profiles, evidence sources and approval authorities.
  • Owns production authorization, incident response, monitoring, continuity and runtime operations.
  • Validates the system in the target environment before making an operational claim.

RESPONSIBLE SECURITY REPORTING

Report suspected vulnerabilities privately.

Do not place credentials, tokens, private keys, proprietary infrastructure details, private repository contents, exploit details or sensitive reproduction material in a public issue or pull request. For supported repositories with GitHub Private Vulnerability Reporting enabled, use the repository's Security → Advisories → Report a vulnerability path.

Report an IaaP Guard vulnerability Support guidance

Automate the work.
Do not automate away accountability.

The security objective is not fewer controls. It is to turn the right controls into repeatable product behavior while keeping approval, authority and accountability visible.
